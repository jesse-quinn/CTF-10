# challenge-integrity Specification

## Purpose
Keep the CTF-10 challenge build self-consistent and tamper-resistant: staged inner build trees stay unreadable to unprivileged in-challenge users, fetched binaries are integrity-checked, and challenge content contains no vestigial or misleading artifacts that create unintended solution paths.

## Requirements

### Requirement: Staged inner build tree is protected on the outer host

Inner-stack secrets, keys, and flag values staged under the outer host SHALL
NOT be readable by the unprivileged outer account, and the staged tree SHALL NOT
live under any player's home directory.

#### Scenario: Unprivileged outer account cannot read the staged inner stack

- **WHEN** the unprivileged outer account (`iris`) enumerates the outer
  filesystem before performing the intended escalation
- **THEN** it cannot read the inner stack's secrets, credential notes, first
  inner flag source, or breakout notes, because the staged tree lives outside
  any player home at `root:root` mode `0700`.

#### Scenario: Inner stack still builds from its new location

- **WHEN** the outer entrypoint runs `docker compose` against the relocated
  stack path
- **THEN** the inner gallery image builds and starts exactly as before, with
  every flag still reachable by its intended reader.

### Requirement: Reproducible build pins and integrity checks

Base images, language packages, and any fetched static binary the documented
exploit depends on SHALL be pinned, and a static binary fetched over the network
SHALL be integrity-checked against a known digest so the challenge builds
reproducibly.

#### Scenario: Fetched static Docker CLI is verified

- **WHEN** the gallery image build fetches the static Docker CLI tarball over
  the network
- **THEN** the build verifies the tarball against a per-architecture SHA-256 and
  fails the build if the digest does not match.

#### Scenario: sshd host keys are generated deterministically

- **WHEN** the gallery image is built
- **THEN** its sshd host keys are generated by an explicit `ssh-keygen -A` in the
  build rather than relying on package postinst behaviour, so sshd always starts.

### Requirement: Challenge content is self-consistent

The challenge content SHALL NOT ship installed-but-unconfigured tooling that
misleads a player, nor any vestigial reference to an unrelated challenge, so the
files describe only this challenge's actual behaviour.

#### Scenario: No unconfigured misleading tool

- **WHEN** a player inspects the installed packages in the gallery container
- **THEN** there is no installed-but-unconfigured privilege tool (such as an
  unconfigured `sudo`) presented as if it were part of the intended path.

#### Scenario: No cross-challenge vestige

- **WHEN** a maintainer reads the gallery build comments
- **THEN** they describe this challenge's single non-root user model and contain
  no reference to accounts from unrelated challenges.
